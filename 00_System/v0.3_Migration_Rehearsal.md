## Failure injection and rollback

After apply, the rehearsal appended a marker to COM-anthropic and requested rollback.
The engine refused with `rollback precondition changed`, proving that it did not
silently overwrite post-migration drift. The changed file remained untouched by the
failed rollback.

The target was then restored to its recorded after-hash and rollback was retried.

The failure injection was deliberate test data in the disposable clone. It was not a

## Decision

F-018 passes. The existing migration framework can plan and apply the selected v0.2
legacy Company compatibility change, reject rollback when target bytes drift, and
restore the full formal-object set byte-for-byte without changing Candidate DB v2.
Production migrations still require their own reviewed plan, dry-run, explicit
`--apply`, backup manifest, and human authorization.
