日期：2026-08-16
目标：`http://127.0.0.1:8765`
模式：只读审计；未提交表单，未执行仓库写入

## 1. 范围冻结

## 2. 总体判断

网站已经具备大部分底层能力，预览 -> 确认 -> 提交边界整体是连贯的。当前最大的产品风险不再是后端能力缺失，而是：多个能力无法被用户发现，部分链接丢失作用域或直接报错，许多详情/创建页面仍展示内部 Markdown 或 JSON，而不是面向用户的工作流。

因此，最有价值的修复应先处理确定性产品问题：路由、项目作用域、入口、选择控件、结构化表单和响应式布局。AI 只应用于语言理解确实有优势的地方：评审建议、实体/板块匹配解释、来源预填、证据草稿和研究质量诊断。

## 3. 已验证基线

- 13 个一级页面在审计期间均返回 HTTP 200。
- 一级页面爬取到 339 个唯一的本地 GET 链接，其中 29 个返回非 200。
- 其中 24 个非 200 是评审队列对象链接：22 个 Impact Assertion 和 2 个 Ontology Assertion。
- 另外 5 个非 200 由全局健康页产生，原因是把显示标签 `全局` 当成了项目 ID。
- 当前热请求耗时抽样如下：

| 页面 | 首字节时间 |
|---|---:|
| 决策 | 约 13 ms |
| 健康 | 约 85-156 ms |
| 运营 | 约 66 ms |
| 分析 / 分析指标 | 约 1.05-1.13 s |

当前进程中，决策和健康已经不是主要性能瓶颈；分析页面仍然明显偏慢。

当前已经具备的良好基础：

- 权威写入普遍使用预览和明确确认。
- 全局存在 `:focus-visible` 焦点样式。
- 表格通常被包裹在可键盘聚焦的横向滚动区域中。
- 候选驳回、恢复和提升均保留操作历史。
- 候选建议与已评审证据已经分开。

## 4. 问题清单

### P1 - 正确性和工作流阻断

#### WEB-001：评审队列存在 24 个死链

`object_url()` 对 `impact_assertion` 和 `ontology_assertion` 回退到 `/objects/{id}`，但系统没有 `/objects/{id}` 路由。当前 116 条待评审记录中包含 22 个 Impact Assertion 和 2 个 Ontology Assertion，因此用户无法从评审队列打开这些对象。

修复方向：为所有可评审对象定义统一的规范路由映射，并在队列、引用、搜索结果和详情页中复用。

#### WEB-002：全局健康页破坏导航作用域

全局健康页设置 `selected = "全局"`，然后将其作为 `project_id` 传给 shell。shell 因此生成 `/?project=全局` 一类链接。

实际结果：

- 项目概览返回 404。
- 评审、指标、运营和健康页面在带 `project=全局` 时返回 500。

修复方向：将“显示用的作用域名称”和“查询用的作用域参数”分开。全局作用域必须用 `None` 表示，不能使用翻译后的显示文本。

#### WEB-003：URL 携带了项目作用域，但目标页面没有真正使用

项目概览和指标页会链接到带项目参数的目标，但若干处理器虽然接收参数，却没有应用过滤：

- Impact 忽略 `project`。
- Sources 不接收 `project`。
- Pipeline Sources 不接收 `project`。
- Analysis 接收但不应用 `project`。
- Decision 将 `project` 传给 shell，但快照仍是全局数据。

示例：PRJ-001 显示 45 个 Event 和 144 个 Source，而全局仓库有 54 个 Event 和 156 个 Source。用户点击项目数字后，可能误以为仍在项目范围内，实际看到的却是全局数据。

修复方向：明确标记每个页面是项目级还是全局级。项目级页面必须过滤；全局级页面必须丢弃项目参数，并明确提示作用域已经切换。

#### WEB-004：重要写入工作流只有路由，没有可发现入口

网站后端已经暴露了一些工作流，但所属页面没有可见入口，例如：

- Event 创建。
- Universe 实体和 Ontology Assertion 创建。
- Impact Proposal 创建。
- Analysis Run 和 Thesis Proposal 创建。
- Forecast、Valuation、Scenario 和 Recommendation 创建。
- Project 和 Action 管理只能通过二级页面进入，而这些二级页面本身也没有接入主要产品流程。

因此，Decision 和 Analysis 页面看起来是只读的，尽管系统实际存在写入路由。

修复方向：为每个工作区提供少量明确的操作入口，并复用现有预览/确认流程。不应把所有路由都塞进一级导航。

#### WEB-005：移动端健康页可能整体移出视口

在 375 px 视口下，Health 页面左侧内容被裁切，文档宽度约为 554 px。激活导航项的自动滚动，以及网格/表格的最小内容宽度共同导致了页面横向偏移。Home 和 Source 创建页也出现了文档级横向溢出。

修复方向：为网格子项设置 `min-width: 0`，把溢出限制在表格滚动容器内，保证表单控件宽度安全，并让滚动只发生在导航容器中而不是整个文档。

### P2 - 高影响的可用性和清晰度问题

#### WEB-006：评审批量操作要求手动输入 ID

“预览评审”并不是处理全部 116 条记录，而是让用户手动输入逗号分隔的 ID，并对这些 ID 应用一个决定。后端批量边界本身合理，但 UI 缺少：

- 行复选框和已选数量。
- 选择当前页/清空选择。
- 同类型批次，或对混合类型批次的明确警告。
- 分页和类型构成提示。
- 对实际待评审类型 `impact_assertion` 和 `ontology_assertion` 的筛选。

修复方向：改为复选框选择、固定批量操作区，并在预览中按对象类型分组展示摘要。

#### WEB-007：许多普通工作流默认要求编辑原始 JSON

Project、Action、Entity、Ontology、Impact、Analysis、Forecast、Valuation、Scenario、Recommendation、cadence review、Event 和 Report 主要依赖 JSON 文本框。这暴露了实现契约，而不是用户任务，也使验证错误难以恢复。

修复方向：为常用字段提供结构化表单，少见字段放进“高级 JSON”折叠区。低频开发/诊断工作流可以保留 JSON 优先。

#### WEB-008：详情页仍默认展示原始 Markdown

Thesis、通用 Event/Report/Action/Project、Analysis Run、Decision 详情、评估包和关系输出都使用 `<pre>` 展示内容。这与之前指标页面直接显示 Markdown 的问题相同，只是扩展到了更多详情页。

修复方向：默认渲染类型化分区、元数据分组和链接引用；原始 Markdown 作为次级的审计/源码视图保留。

#### WEB-009：许多状态数字无法进入对应数据

以下显著数字是不可交互的，但用户通常会期待它们可以跳转：

- 管线：已发现、已入库、已驳回和通道就绪。
- 影响：全部断言、待评审、已评审直接断言和冲突。
- 运营：待处理总数。
- 健康：索引漂移、资产失败和失败运行。
- 通道指标：发现、重复和失败。

修复方向：每个运营数字都应链接到对应的筛选结果/锚点；如果没有合理目标，就应明确呈现为不可操作的上下文信息，而不是仪表盘控件。

#### WEB-010：详情页是终点，且丢失列表上下文

Candidate、Analysis Run 和 Decision 详情页缺少或弱化面包屑/返回链接。进入详情后，用户无法保留原来的筛选条件、项目作用域和列表页位置。

修复方向：增加紧凑面包屑和返回 URL，并保留作用域、筛选条件和分页位置。

#### WEB-011：列表页面的规模处理不一致

- Reviews 一次渲染全部 116 行。
- Sources、已入库 Sources、Companies、Sectors 和 Reports 一次渲染全部记录。
- Candidate Queue 有分页，但顶部数字是当前页数量，不是匹配总数。
- Analysis 只展示 10 个 Run，选择器只提供前 20 个，比较对象还会静默限制为两个。

修复方向：统一列表页的 `total`、`shown`、范围、筛选摘要和分页语义。

#### WEB-012：当前导航高亮依赖标题推断

多个子页面会错误高亮到项目概览，例如 Operations discovery/benchmark/export、Brief、Event/Report 创建页和 Decision 详情页。

修复方向：每个页面显式传入 `active_key`，不要根据翻译后的标题推断导航状态。

#### WEB-013：运营 ID 和失败记录通常不可操作

运营中的 Jobs/Actions/Forecast/Recommendation/Review ID，以及管线中的 Channel ID，很多只是纯文本。健康页的失败记录也没有直接的“查看”“重试”或所属工作区链接。

修复方向：将 ID 统一变为规范链接；只有在已有预览/确认变更流程的情况下，才提供操作按钮。

#### WEB-014：来源采集方式不会控制对应字段

在来源创建页从 URL 切换到文件上传后，URL 和文件控件仍然同时显示且可编辑。来源工作台中也存在同类问题。

修复方向：使用分段控件切换采集方式，只显示并启用当前输入；切换回来时保留用户已经输入的值。

#### WEB-015：健康页混合了当前事故、历史记录和配置维度

健康页当前显示 42 个历史失败运行，而产业首页显示当前失败数为 0。即使选中的 DeepSeek Key 已保存在本机模型配置中，健康页仍可能把所有环境变量形式的 API Key 显示为缺失。管线还可能同时显示“20 个通道就绪”，而产业首页显示“20 个通道过期”；两者实际分别表示配置就绪和运行新鲜度，但标签没有解释清楚。

修复方向：分离当前/未解决事故与历史记录；使用当前选中供应商的有效配置；明确命名通道维度，例如“已配置”“可调度”“新鲜”。

#### WEB-016：Analysis 计算了多于实际展示内容的数据

Analysis 每次请求都会评估全部可用 Run 并计算模式指标，但页面只渲染 10 行 Run 和 20 个选择项。带选中 Run 的请求还可能同时构建选中快照和全量快照。这解释了当前约 1.05-1.13 秒的耗时。

修复方向：对 Run 摘要分页，只对可见/选中的 Run 计算评估详情，并按仓库签名缓存不可变的派生摘要。当前瓶颈不是 SQLite。

#### WEB-017：模型配置与 Analysis 创建脱节

模型页可以保存 DeepSeek 配置，但新建 Analysis 和 Replay 表单在 JSON 示例中仍默认使用 `echo`。用户必须知道并重新输入 provider/model 才能使用已配置的真实模型。

修复方向：Analysis 表单默认使用当前有效的供应商/模型，并明确提供“Echo / 已配置模型”两种选择。

#### WEB-018：无障碍和触控目标需要统一检查

全局焦点轮廓和表格滚动区域是良好基础。剩余问题包括模型筛选框/模型选择框缺少程序化标签，以及大量表格链接的实际高度小于 24 px。移动端导航虽然可以横向滚动，但没有清晰提示还有更多目的地。

修复方向：补充程序化标签，增大行链接点击区域，并用紧凑菜单或两级工作区切换器替代对移动端横向导航的依赖。

### P3 - 一致性和细节问题

- 中英文标签混用，但没有稳定的术语规范。
- Source 列表使用 `class="button"`，而样式表只定义了 `button-link`。
- 空状态通常只显示“无记录”，很少提供下一步有效操作。
- 表格在用户尚未要求诊断详情前，就展示哈希、内部字段名和很长的错误文本。
- Hero 卡片和面板阴影保持一致，但运营页面需要更密集、更面向任务的布局，减少重复说明面板。

## 5. AI 增强机会

所有 AI 功能都应遵循以下不变量：

```text
AI 生成建议/草稿
-> 人工查看/修改/忽略
-> 现有确定性预览
-> 人工明确确认
-> 按现有规则进入 pending 或 reviewed 状态
```

AI 输出不得自动批准 Evidence、提高 Thesis 置信度、创建权威事实或生成可执行的投资动作。

### AI-001：评审助手（第一优先级）

先从 Source 评审开始，生成结构化建议：

- 元数据完整性和出处缺口。
- 来源等级建议及理由。
- 重复概率和匹配的 Source ID。
- 实体/板块匹配建议。
- 资产/引用完整性观察。
- 建议批准/修改/拒绝的决定及明确理由。

建议应填充可见字段，但不能提交现有评审预览。Source 质量稳定后，再扩展到 Event 和 Impact。

### AI-002：候选实体/板块重排与解释

当前确定性匹配器使用候选标题、发布方别名和板块关键词。AI 只应处理歧义、未知或低置信度情况：

- 对一个小规模的确定性候选集进行排序。
- 引用支持每个匹配的标题/内容片段。
- 展示竞争实体/板块和相反线索。
- 允许研究者选择、清除或搜索其他匹配。
- 人工选择后重新执行确定性优先级评分。

不能让模型自行发明实体 ID 或绕过 Universe 注册表。

### AI-003：来源摄取助手

根据 URL 或上传资产，建议标题、发布方、发布日期、来源类型/等级、实体、板块、摘要和可能重复项。建议应填入可见字段；发布日期仍保持 proposal，直到用户确认。

### AI-004：Event 和 Impact 草稿助手

根据已处理 Source 草拟 Fact 锚点、Event 字段、替代解释、未知项和后续指标。根据已评审 Event 草拟 Impact 机制、时间范围、反向因素和证据链接。所有输出保持 pending，并使用现有预览流程。

### AI-005：研究质量助手

在项目概览、指标和健康页，根据确定性缺口生成简短的优先工作清单：

- 缺少有效资产或完整出处的 Source。
- 缺少反面证据的 Thesis。
- 只有单一证据链支持的 Assertion。
- 过期的 Recommendation 和到期 Forecast。
- 无法形成 Source -> Event -> Thesis/Impact -> Decision 链路的对象。

事实应由确定性检查提供；模型只负责解释和排序。

### AI-006：Analysis 启动器和比较摘要

根据研究问题建议 Analysis Mode、作用域和输入 ID。默认使用已配置模型，解释每个输入为什么被选中，并允许用户在预览前修改。对于已完成的 Run，摘要展示一致点、分歧点、证据遗漏和需要人工解决的问题。

### AI-007：Decision 复盘助手

在 Forecast 和 Recommendation 复盘时，比较新旧证据，检查触发条件/证伪条件，列出未解决未知项，并建议下一次复盘日期。不能自动设置研究姿态、方向或结果。

### AI-008：轻量检索，后置

命令面板或自然语言对象查找可以帮助定位 Source、Event、企业和决策。只有在精确 ID/标题/标签搜索被证明不足后再引入向量基础设施；当前单用户规模不值得使用重型检索栈。

## 6. 不应使用 AI 的部分

- 路由、导航高亮和项目作用域。
- 分页、选择、筛选和表单校验。
- 重复哈希、资产完整性和仓库校验。
- 状态转换、预览令牌和审计写入。
- 输入确定后执行的确定性评分计算。
- 当前事故与历史事故的分类。

这些部分应保持可预测、可测试。

## 7. 建议的统一修复工作包

后续实现保持四个顶层工作包：

1. **正确性与信任：** 规范对象路由、全局/项目作用域、显式导航高亮、状态语义和可见入口。
2. **功能闭环：** 评审选择、常用结构化表单、来源模式切换、列表/详情返回上下文和分页语义。
3. **响应式与性能：** 移动端溢出/导航、触控目标、表格密度、Analysis 读模型边界和派生摘要缓存。
4. **AI 辅助：** 先实现 Source 评审助手和候选匹配解释；Source 预填、Event/Impact 草稿和 Decision 复盘放到前两项通过人工验收后再做。

新增顶层任务只能用于已有测试失败、数据损坏/丢失风险或确认的安全漏洞。其他问题应作为这四个工作包下的 backlog 项保留。

## 8. 修复阶段建议验收门槛

- 一级页面和一级详情页面产生的非 200 链接为零。
- 不再使用翻译后的显示标签作为查询标识符。
