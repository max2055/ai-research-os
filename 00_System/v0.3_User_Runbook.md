# AI Research OS v0.3 Web Product and Migration Runbook

Status: engineering baseline
Updated: 2026-08-18
Scope: F-019 current operation + RCP-v03-011 Web-only migration

The website is the only user-facing product interface. Markdown remains authoritative
for research objects; Candidate SQLite, `operations.db`, indexes, Web views, and metrics
are operational or derived state. Operations scheduling is fully website-hosted:
starting the website starts one supervised Worker and stopping it stops scheduled work.
Command blocks in this document are retained only for implementers,
diagnostics, tests, and disaster recovery during migration; they are not the product UX.
Their preview/explicit apply semantics define safety behavior that Web workflows must
preserve without exposing CLI terminology to users.

checks, and `pytest -m "not local_integration"`. It has read-only contents permission
and receives no raw Source assets, Candidate DB, backup identity, provider key, cache,

bytes; it does not make those bytes valid.

## Cost and health

Set the monthly model/API budget only in the process environment or an ignored local
service configuration:

```bash
export RESEARCH_OS_MODEL_COST_BUDGET=100
```

Health aggregates `discovery_runs.cost_estimate` for the current natural month using
Decimal arithmetic. The six states are `unconfigured`, `no_data`, `ok`, `warning`,
`exceeded`, and `invalid`. `warning` begins at exactly 80% of budget and `exceeded` at
exactly 100%. Missing cost is not zero: Health reports known total, unknown count, and
invalid count separately. The Dashboard shows budget presence and utilization, not the
raw configured budget value.

## Backup

### Local Candidate snapshot

Open `/operations/backups`, choose Candidate snapshot, preview and confirm. The Worker
creates an immutable local SQLite snapshot, SHA-256 manifest, and database run record.

Success requires manifest hash, schema version, SQLite integrity `ok`, and a fresh age
result. This local snapshot does not protect against device loss.

### Durable encrypted backup

Follow `00_System/Recovery_Runbook.md` once to install `age`/`gh`, create the fixed
private prerelease, generate two independent identities, and store the second private
identity offline. `09_Automation/operational/durable_backup.json` contains only the
private repository name and public recipients; restore receives a private identity
separately. Start a durable backup from `/operations/backups`; no browser field accepts
the config path, recipient or token.

The Worker encrypts the Candidate and operations SQLite snapshots in the candidate set
and Source assets in the second set, uploads immutable ciphertext plus outer manifests
to the private `research-os-durable-backups-v1` prerelease, verifies remote metadata,
advances the local receipt, and writes one redacted database run. Copy the per-backup receipt to secure
off-device metadata custody; it is ignored by Git but required by the current
verify/restore CLI.

The 24-hour RPO is monitored from the local durable receipt. Missing, failed, invalid,
or stale durable status produces P1 alerts `BKP_DURABLE_MISSING`,
`BKP_DURABLE_FAILED`, `BKP_DURABLE_INVALID`, or `BKP_DURABLE_STALE`. Dashboard render
does not call GitHub; use `verify-remote` for explicit network verification.

## Restore

1. Clone the private Git repository at the intended commit and install the pinned
   environment plus `age`, `gh`, and `jq`.
2. Restore the ignored backup config, selected per-backup receipt, and one matching
   private identity from separate custody.
3. Verify remote ciphertext, dry-run restore, then apply only to an absent or empty
   disposable destination:

```bash
BACKUP_CONFIG=09_Automation/operational/durable_backup.json
AGE_IDENTITY=/Users/max/.config/ai-research-os/backup/age-identity.txt
RESTORE_DESTINATION=09_Automation/operational/restores/$BACKUP_ID
research-os backup durable verify-remote --backup-id "$BACKUP_ID" \
  --config "$BACKUP_CONFIG"
research-os backup durable restore --backup-id "$BACKUP_ID" \
  --identity "$AGE_IDENTITY" \
  --destination "$RESTORE_DESTINATION" \
  --config "$BACKUP_CONFIG"
research-os backup durable restore --backup-id "$BACKUP_ID" \
  --identity "$AGE_IDENTITY" \
  --destination "$RESTORE_DESTINATION" \
  --config "$BACKUP_CONFIG" --apply
```

4. Inspect the verified disposable result. Copy the Candidate and operations snapshots
   to `09_Automation/operational/candidates.db` and
   `09_Automation/operational/operations.db` only when integrity/schema/hash checks pass
   and no unexplained live file would be overwritten. Merge Source assets only when
   existing hashes agree.
5. Restore other ignored local config and secrets from their own secure store.
6. Start `python -m research_os.ui`; do not load the legacy OS scheduler.
7. Run asset verification, strict validation, index rebuild/check, full tests, Ruff,
   mypy, website/Worker lifecycle smoke, and confirm run count is unchanged while the
   website is stopped.

```bash
PYTHONPATH=src /Users/max/.venvs/ai-research-os/bin/python -m research_os --root . source verify-assets
PYTHONPATH=src /Users/max/.venvs/ai-research-os/bin/python -m research_os --root . index --apply
```

Use `00_System/Recovery_Runbook.md` and `00_System/v0.3_Recovery_Drill.md` as the

## Failure response

| Priority | Trigger | Immediate action | Escalation |
|---|---|---|---|
| P0 | suspected secret exposure, authoritative data loss, or Web mutation that bypasses actor/preview/audit controls | stop jobs/UI, preserve logs, rotate affected secret, make no cleanup write | owner immediately; security/recovery review before restart |
| P1 | validation errors, Candidate DB integrity failure, hash mismatch, durable backup missing/failed/invalid/stale beyond the 24-hour RPO, or repeated Source corruption | stop applies and discovery, preserve files/receipt/Job, verify remote, restore to a disposable copy first | owner same session; open Action and recovery evidence |
| P2 | one Channel/job failure, stale lock, index drift, overdue review, or stale data | disable affected Channel if needed, retry safely after root cause, rebuild derived index | weekly review if not resolved that day |
| P3 | usability issue, slow query inside SLO, or documentation mismatch | record reproducible details and continue unaffected work | backlog/monthly review |

Safe retry means the operation is idempotent or its prior Job/action state has been
checked. Never delete a lock, backup, Candidate action, Source asset, or migration
manifest merely to make a retry succeed.

## Secrets and Escalation

Keep secrets outside Git and outside research objects. Health and Operations must
show presence/status only, never values. Escalate any suspected disclosure as P0.
RCP-v03-011 already approves controlled Web mutation. Escalate any mutation that lacks
named actor, preview, explicit confirmation, target version, audit, rollback, or required
human authority. Exposing the UI beyond loopback, changing research rules/taxonomy,
approving evidence automatically, increasing Thesis confidence automatically, or adding
trading execution still requires a separate explicit human governance decision.
